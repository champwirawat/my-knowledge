# คู่มือเริ่มต้น Supabase Local Development (Supabase Local Dev Beginner Guide)

คู่มือการรัน **Supabase บนเครื่องตัวเองด้วย Docker** สำหรับผู้เริ่มต้น ครอบคลุมตั้งแต่การติดตั้ง การเปิด/ปิดระบบ การเชื่อมต่อแอป ไปจนถึงกระบวนการทำงาน (Workflow) ในการจัดการ Migration และข้อมูลทดสอบ (Seed Data) โดยไม่ระบุเจาะจงเฉพาะโปรเจกต์ใดโปรเจกต์หนึ่ง

---

## 1. ทำไมต้องรัน Supabase บนเครื่องตัวเอง?

แม้ว่าการพัฒนาโปรเจกต์โดยการเชื่อมต่อตรงไปยัง Supabase Cloud จะทำได้ง่าย แต่การรันในเครื่อง local ดีกว่าในหลากหลายแง่มุม:

*   **รวดเร็ว** — คำสั่งคิวรีวิ่งในเครื่องตัวเอง ไม่มีปัญหาความล่าช้าจากเครือข่าย (Network Latency)
*   **ปลอดภัยต่อข้อมูล** — ทดลองดัดแปลง สร้าง หรือลบตารางได้อิสระโดยไม่ส่งผลกระทบต่อคนในทีมหรือฐานข้อมูลจริง
*   **ไม่ติดโควต้าการใช้งาน** — หลีกเลี่ยงข้อจำกัดการหยุดทำงานชั่วคราว (Pause Project) ของบริการฟรีบน Cloud
*   **ทดสอบการส่งอีเมลได้สมบูรณ์** — อีเมลยืนยันการสมัครสมาชิกหรือกู้คืนรหัสผ่านจะถูกดักและแสดงผลในเครื่องทันทีโดยไม่มีการยิงอีเมลจริงไปหาผู้ใช้
*   **พัฒนาแบบ Offline ได้** — ไม่ต้องเชื่อมต่ออินเทอร์เน็ตก็เขียนโค้ดต่อได้

**สิ่งที่ควรรู้:** Supabase ไม่ได้ทำงานอยู่บน Docker container เพียงตัวเดียว แต่เป็นการรวมตัวของบริการนับสิบตัว (เช่น PostgreSQL, GoTrue/Auth, PostgREST, Storage, Realtime, Studio, Kong gateway, Mailpit) ดังนั้น **อย่าพยายามรัน Docker Container เหล่านี้ด้วยตนเอง** แต่ควรสั่งผ่านเครื่องมือ **Supabase CLI** ซึ่งจะคุมระบบ container ทั้งหมดให้อย่างอัตโนมัติ

```
คุณ ──▶ supabase CLI ──▶ Docker ──▶ [Postgres] [Auth] [PostgREST] [Storage]
                                    [Realtime] [Studio] [Kong] [Mailpit] ...
```

## 2. ขั้นตอนการติดตั้ง

เราต้องมีเครื่องมือหลัก 2 อย่างติดตั้งอยู่ในเครื่องคอมพิวเตอร์:

### 2.1 Docker
ติดตั้งโปรแกรม [Docker Desktop](https://www.docker.com/products/docker-desktop/) (สำหรับ macOS/Windows) หรือติดตั้ง Docker Engine (สำหรับ Linux) จากนั้นเปิดโปรแกรมให้พร้อมรันอยู่
```bash
docker --version    # ตรวจสอบว่า Docker ติดตั้งสำเร็จ
```

### 2.2 Supabase CLI
```bash
# macOS (ติดตั้งผ่าน Homebrew)
brew install supabase/tap/supabase

# หรือจะติดตั้งเป็น Dependency ในโฟลเดอร์โปรเจกต์
npm install -D supabase          # แล้วเรียกใช้ผ่านคำสั่ง npx supabase ...

# ตรวจสอบการติดตั้ง
supabase --version
```

### 2.3 ตั้งค่าโครงสร้างในโปรเจกต์ (รันครั้งเดียว)
ที่ Root ของโปรเจกต์ที่เรากำลังพัฒนา หากยังไม่มีโฟลเดอร์การตั้งค่าของ Supabase ให้สั่งรันคำสั่ง:
```bash
supabase init
```
จะได้โครงสร้างไฟล์และโฟลเดอร์ใหม่เกิดขึ้นดังนี้:
```
supabase/
├── config.toml      # ไฟล์ตั้งค่า local stack (เช่น ports, auth settings, storage)
├── migrations/      # โฟลเดอร์เก็บไฟล์ประวัติ SQL migration
└── seed.sql         # (ถ้าต้องการ) สคริปต์สำหรับป้อนข้อมูลจำลองตอนเริ่มต้น
```
*โฟลเดอร์ `supabase/` นี้ควรบันทึก (commit) เข้าไปยัง git repository เสมอ เนื่องจากเป็นบันทึกข้อกำหนดโครงสร้างตารางของระบบที่สมาชิกในทีมทุกคนต้องใช้งานร่วมกัน*

## 3. การเปิดใช้งาน: `supabase start`

พิมพ์คำสั่งเพื่อสั่งเริ่มการทำงานของบริการทั้งหมดในเครื่อง:
```bash
supabase start
```
*หมายเหตุ: ในการสั่งรันครั้งแรก ระบบจะใช้เวลาระยะหนึ่งเพื่อดาวน์โหลด Docker Images ของบริการต่าง ๆ ลงมาเก็บในเครื่อง* เมื่อเตรียมระบบเสร็จสิ้น CLI จะแสดงหน้าจอสรุป URL และคีย์ชุดหลักที่จำเป็นสำหรับการเชื่อมต่อ:

```
          API URL: http://127.0.0.1:54321
           DB URL: postgresql://postgres:postgres@127.0.0.1:54322/postgres
       Studio URL: http://127.0.0.1:54323
      Mailpit URL: http://127.0.0.1:54324
         anon key: eyJhbGciOiJIUzI1NiIs...
 service_role key: eyJhbGciOiJIUzI1NiIs...
```

### รายละเอียดและหน้าที่ของแต่ละส่วน:

| บริการ/คีย์ | รายละเอียดการใช้งาน |
| --- | --- |
| **API URL** | ลิงก์กลางในการเชื่อมต่อ — ใช้ป้อนใส่แอปพลิเคชันแทนลิงก์ของ Cloud |
| **DB URL** | ใช้สำหรับการล็อกอินเข้าจัดการ PostgreSQL ดิบ ผ่านโปรแกรม GUI เช่น TablePlus, DBeaver หรือ pgAdmin |
| **Studio** | หน้า Dashboard จัดการหลังบ้านของ Supabase — ทำหน้าที่ส่องดูตาราง, เขียนรัน SQL หรือตรวจแก้ข้อมูล |
| **Mailpit** | ตู้จดหมายจำลอง — อีเมลทั้งหมดที่ระบบ Auth ในเครื่องสั่งส่งออก จะมารวมอยู่ในหน้าจอนี้ทั้งหมด |
| **anon / service_role key** | คีย์สำหรับป้อนในแอปพลิเคชันเพื่อการเข้าถึงข้อมูล (คีย์ในเครื่องนี้จะไม่เป็นความลับ มีลักษณะเหมือนกันทุกเครื่อง) |

*เมื่อรันคำสั่งเปิดใช้งาน ระบบจะทำการ apply ไฟล์ Migration ทุกตัวที่อยู่ในโฟลเดอร์ `supabase/migrations/` เข้าตารางในเครื่องให้อัตโนมัติทันที*

คำสั่งอื่น ๆ ที่เกี่ยวข้อง:
```bash
supabase status    # ตรวจสอบดูสถานะ และดูรายการ URL/Keys ของโปรเจกต์
supabase stop      # สั่งปิด Container บริการทั้งหมดในเครื่องชั่วคราว (ระบบจะแบคอัพข้อมูลเก็บไว้ให้)
```

## 4. วิธีผูกโปรเจกต์เข้ากับระบบเครื่องตัวเอง (Local Connection)

แก้ไขค่าในไฟล์ config ตัวแปรสิ่งแวดล้อมฝั่ง Client ของแอปพลิเคชัน (เช่น `.env.local` ใน Next.js) ชี้มาที่ค่าในเครื่องแทน:
```bash
# .env.local (ชี้มาที่ local stack)
NEXT_PUBLIC_SUPABASE_URL=http://127.0.0.1:54321
NEXT_PUBLIC_SUPABASE_ANON_KEY=<นำค่า anon key จากหน้าจอ supabase start มาวาง>
```

**ข้อควรระวัง:**
*   ระวังการเผลอ commit ไฟล์การตั้งค่าที่มีการใส่คีย์ของ Cloud จริงทับไฟล์การตั้งค่าในเครื่อง
*   โค้ดการเชื่อมต่อฐานข้อมูลในแอปพลิเคชันไม่จำเป็นต้องเปลี่ยนแปลงใด ๆ เนื่องจาก SDK ของ Supabase รองรับการทำงานเหมือนเดิมทุกประการ แค่เปลี่ยนจุดเชื่อมต่อ URL ปลายทางเท่านั้น

## 5. กระบวนการแก้ไขโครงสร้างตาราง (Migration Workflow)

ในการพัฒนา เราจะใช้วิธี **แก้ไขในเครื่อง local → ตรวจสอบผลลัพธ์ → ทำเป็นประวัติไฟล์ Migration → อัปเดตขึ้นระบบจริง** โดยมีวิธีการสร้างไฟล์ประวัติ 2 วิธีหลักดังนี้:

### วิธีที่ 1: เขียนสคริปต์ SQL เอง (แนะนำเพื่อให้ควบคุมโค้ดได้สมบูรณ์)
1.  พิมพ์คำสั่งเพื่อสร้างสคริปต์ Migration เปล่า:
    ```bash
    supabase migration new add_tasks_table
    ```
2.  ระบบจะสร้างไฟล์ใหม่ชื่อเช่น `supabase/migrations/<timestamp>_add_tasks_table.sql` ให้เราเข้าไปเขียนโค้ดสร้างตารางหรือเปลี่ยนฟิลด์ SQL ในไฟล์นี้
3.  ทดสอบระบบด้วยการรีเซ็ตฐานข้อมูลใหม่ตั้งแต่ศูนย์ เพื่อยืนยันว่าสคริปต์รันได้ไร้ข้อผิดพลาด:
    ```bash
    supabase db reset
    ```

### วิธีที่ 2: ดัดแปลงตารางผ่าน UI Studio แล้วให้ระบบช่วยเทียบ
1.  เปิดหน้าเว็บ Studio ในเครื่อง (`http://127.0.0.1:54323`) แล้วกดแก้ไขหรือสร้างตารางผ่านหน้าจอ UI จนพอใจ
2.  สั่งให้ CLI สแกนตรวจหาสิ่งที่แก้และเขียนสรุปเป็นไฟล์ Migration ให้:
    ```bash
    supabase db diff -f add_tasks_table
    ```
3.  รันคำสั่ง `supabase db reset` เพื่อยืนยันว่าสคริปต์สร้างขึ้นมาใหม่สามารถใช้งานได้จริง

### เมื่อพร้อมจะอัปเดตโครงสร้างขึ้นเซิร์ฟเวอร์ Cloud จริง
```bash
# 1. เชื่อมต่อโปรเจกต์ local เข้ากับ Cloud (ทำเฉพาะครั้งแรก)
supabase link --project-ref <รหัส-project-ref-ของ-cloud>

# 2. ดันไฟล์ Migration ที่อยู่ในเครื่องและ Cloud ยังไม่มีขึ้นไปประมวลผล
supabase db push
```

*หลีกเลี่ยงการเข้าไปสร้างและดัดแปลงตารางบน Cloud Dashboard ตรง ๆ เพราะจะทำให้โครงสร้างระหว่างเครื่อง local และ Cloud ไม่ตรงกัน ซึ่งสร้างปัญหาในอนาคต หากมีการแก้ไขไปแล้ว ให้รันคำสั่ง `supabase db pull` เพื่อดึงความแตกต่างกลับมาเก็บเป็น Migration ในเครื่อง*

## 6. ข้อมูลในเครื่องจัดเก็บที่ไหน และข้อมูลหายเมื่อไร?

ข้อมูลจำลองที่ใช้งานในเครื่องจะถูกจัดเก็บอยู่ใน Docker volumes ซึ่งจะไม่สูญหายไปเมื่อมีการปิดโปรแกรมปกติ:

| สถานการณ์ | ข้อมูลในฐานข้อมูล |
| --- | --- |
| รันคำสั่ง `supabase stop` | **ข้อมูลอยู่ครบ** สตาร์ทใหม่ข้อมูลกลับมาแสดงตามเดิม |
| ปิดคอมพิวเตอร์ / ปิดโปรแกรม Docker Desktop | **ข้อมูลอยู่ครบ** |
| รันคำสั่ง `supabase stop --no-backup` | **ข้อมูลหายทั้งหมด** (เป็นการเจตนาล้างข้อมูลและ container) |
| รันคำสั่ง `supabase db reset` | **ข้อมูลหายทั้งหมด** โดยระบบจะสแกนรัน Migration ใหม่หมดตั้งแต่ต้น พร้อมป้อนสคริปต์ข้อมูลใน `seed.sql` |

### สคริปต์ป้อนข้อมูลจำลอง `seed.sql`
เนื่องจากการ reset ฐานข้อมูลจะส่งผลให้ข้อมูลจำลองที่เรากรอกทดสอบไว้หายไป วิธีแก้ไขคือเขียนคำสั่งเขียนข้อมูลจำลองลงในไฟล์ `supabase/seed.sql` เพื่อให้ระบบนำมาป้อนข้อมูลเข้าให้อัตโนมัติทุกครั้งที่ฐานข้อมูลมีการรีเซ็ต:
```sql
-- supabase/seed.sql
insert into public.categories (name) values ('งานบ้าน'), ('งานซ่อมแซม'), ('ทำความสะอาด');
```

## 7. การทดสอบการสมัครสมาชิกและรับอีเมลผ่าน Mailpit

เมื่อผู้ใช้สมัครสมาชิกผ่านหน้าแอปในเครื่อง local และระบบถูกตั้งค่าให้ยืนยันตัวตนผ่านอีเมล เราจะไม่ได้รับอีเมลในกล่องจดหมายจริง แต่อีเมลนั้นจะถูกส่งมารวมอยู่ในระบบดักจับจดหมายของ **Mailpit** ที่ลิงก์ `http://127.0.0.1:54324`

ขั้นตอนการทดสอบ:
1.  กดสมัครสมาชิกบนหน้าจอแอปพลิเคชันด้วยอีเมลจำลองใด ๆ
2.  เปิดเข้าไปที่หน้าต่าง Mailpit ในเบราว์เซอร์
3.  เห็นกล่องข้อความยืนยันตัวตน ให้กดลิงก์กู้คืนหรือลิงก์ยืนยันในหน้านั้นเพื่อทำรายการต่อ
4.  กลับไปทดสอบล็อกอินเข้าใช้แอปได้ตามปกติ

*หากไม่ต้องการยืนยันตัวตนทางอีเมลเลยในขั้นตอนการพัฒนา สามารถสั่งปิดการส่งอีเมลได้ในไฟล์ `supabase/config.toml`:*
```toml
[auth.email]
enable_confirmations = false
```
*(หลังจากแก้ไขไฟล์ `config.toml` จะต้องสั่ง `supabase stop` และ `supabase start` ใหม่เพื่ออัปเดตการตั้งค่า)*

## 8. สรุปชุดคำสั่งใช้งานบ่อย

```bash
# การเปิด-ปิดระบบในแต่ละวัน
supabase start                        # รันระบบและอัปเดต migration อัตโนมัติ
supabase status                       # ส่องดูลิงก์ URL และ Keys ทั้งหมด
supabase stop                         # สั่งปิดระบบชั่วคราว (เก็บข้อมูลไว้)

# จัดการ Migration ตาราง
supabase migration new <ชื่อไฟล์>      # สร้างไฟล์เขียน SQL Migration เปล่า
supabase db diff -f <ชื่อไฟล์>         # สร้างสคริปต์ Migration จากความต่างบนบราวเซอร์
supabase db reset                     # เคลียร์ฐานข้อมูล รัน Migration และ Seed ใหม่หมด
supabase migration list               # ส่องประวัติเปรียบเทียบตารางเครื่อง local และ Cloud

# ซิงก์ขึ้นระบบ Cloud
supabase link --project-ref <รหัส>     # ผูกระบบ local เข้ากับโปรเจกต์คลาวด์
supabase db push                      # ส่งประวัติโครงสร้างตารางใหม่ขึ้น Cloud
supabase db pull                      # ดึงโค้ดโครงสร้างที่เผลอปรับบนคลาวด์กลับลงมาเป็นไฟล์

# สร้างประเภทข้อมูล (Types) จากฐานข้อมูลมาใช้งานใน TypeScript
supabase gen types typescript --local > src/types/database.types.ts
```
