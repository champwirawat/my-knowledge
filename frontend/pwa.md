# คู่มือเริ่มต้นใช้งาน PWA (Progressive Web App Beginner Guide)

คู่มือการเรียนรู้ **Progressive Web App (PWA)** สำหรับผู้เริ่มต้นฉบับนี้จัดทำขึ้นเพื่อให้เข้าใจแนวคิดพื้นฐาน องค์ประกอบสำคัญ และขั้นตอนการตั้งค่าจริงแบบทีละขั้นตอน โดยมุ่งเน้นไปที่การปูพื้นฐานเพื่อให้สามารถนำไปประยุกต์ใช้กับโปรเจกต์ Next.js ทั่วไปได้

---

## 1. PWA คืออะไร?

**Progressive Web App (PWA)** คือเว็บแอปพลิเคชันที่ถูกเสริมความสามารถให้ทำงานได้ใกล้เคียงกับแอปพลิเคชันดั้งเดิม (Native App) โดยยังคงเป็นเว็บไซต์ปกติที่รันผ่านเบราว์เซอร์ ไม่ต้องผ่าน App Store/Play Store คุณสมบัติเด่นที่ PWA มอบให้ ได้แก่:

*   **ติดตั้งได้ (Installable):** ผู้ใช้สามารถกดเพิ่มไปยังหน้าจอโฮม ("Add to Home Screen") หรือติดตั้งแอปเพื่อให้มีไอคอนอยู่บนหน้าจอเครื่องเหมือนแอปทั่วไป
*   **เปิดแบบเต็มจอ (Standalone Display):** เมื่อเปิดจากไอคอนที่ติดตั้งไว้ จะแสดงผลแบบไม่มี Address Bar หรือปุ่มควบคุมของเบราว์เซอร์ ดูเหมือนแอป Native
*   **ทำงานได้แม้ไม่มีอินเทอร์เน็ต (Offline Capability):** สามารถเก็บแคชไฟล์ static หรือหน้าเว็บไว้ล่วงหน้า ทำให้เปิดใช้งานแอปเบื้องต้นได้แม้เน็ตหลุด
*   **โหลดเร็วขึ้น (Performance):** ไฟล์ JS/CSS/รูปภาพที่ถูกแคชไว้แล้วจะไม่ต้องโหลดใหม่ทุกครั้ง ช่วยลดความล่าช้าในการเปิดหน้าเว็บ

องค์ประกอบหลักที่ทำให้เว็บไซต์กลายเป็น PWA มี 3 อย่าง:

1.  **Web App Manifest** — ไฟล์ JSON สำหรับระบุข้อมูล metadata ของแอป (เช่น ชื่อ, ไอคอน, สีธีม, โหมดการแสดงผล)
2.  **Service Worker** — สคริปต์ JavaScript ที่รันอยู่เบื้องหลังของเบราว์เซอร์ ทำหน้าที่ดักจับ request และตัดสินใจว่าจะตอบกลับด้วยไฟล์จาก Cache หรือดึงจาก Network จริง
3.  **HTTPS** — PWA บังคับให้บริการผ่าน HTTPS เท่านั้น (ยกเว้น `localhost` ตอนพัฒนาในเครื่อง) เนื่องจาก Service Worker มีสิทธิ์ดักจับทุก request จึงต้องปลอดภัยจากการถูกโจมตีแบบ Man-in-the-Middle

## 2. Web App Manifest

**Manifest** คือไฟล์ JSON (สำหรับ Next.js App Router สามารถใช้ไฟล์ `app/manifest.ts` เพื่อเขียนเป็น Object แล้วให้ framework สร้างเป็นไฟล์ JSON ให้โดยอัตโนมัติ) เพื่อระบุรายละเอียดของแอปและสไตล์เมื่อแอปถูกติดตั้ง

ตัวอย่างไฟล์ Manifest พื้นฐาน:
```json
{
  "name": "My Awesome App",
  "short_name": "Awesome",
  "description": "แอปตัวอย่างสำหรับสาธิตการตั้งค่า PWA",
  "start_url": "/",
  "display": "standalone",
  "background_color": "#ffffff",
  "theme_color": "#0ea5e9",
  "icons": [
    { "src": "/icons/icon-192.png", "sizes": "192x192", "type": "image/png" },
    { "src": "/icons/icon-512.png", "sizes": "512x512", "type": "image/png" },
    { "src": "/icons/icon-maskable-512.png", "sizes": "512x512", "type": "image/png", "purpose": "maskable" }
  ]
}
```

### คำอธิบายฟิลด์สำคัญ:
*   `name` / `short_name`: ชื่อเต็ม (แสดงตอนผู้ใช้กดติดตั้ง) และชื่อย่อ (แสดงใต้ไอคอนบนหน้าจอโฮม ซึ่งควรสั้นและกระชับ)
*   `start_url`: หน้าแรกที่ต้องการให้เปิดเมื่อผู้ใช้กดไอคอนแอป
*   `display`: โหมดการแสดงผลของหน้าจอ (ดูหัวข้อ 2.1)
*   `theme_color`: สีของแถบสถานะ (Status Bar) หรือแถบเบราว์เซอร์
*   `background_color`: สีพื้นหลังของ Splash Screen ตอนที่แอปกำลังเริ่มโหลด
*   `icons`: รูปภาพไอคอนของแอป ซึ่งต้องมีขนาด `192x192` และ `512x512` พิกเซลเป็นอย่างน้อยเพื่อผ่านเกณฑ์การติดตั้ง (Installable) ของ Chrome

### 2.1 โหมดการแสดงผล (Display Modes)

| ค่า | พฤติกรรม |
| :--- | :--- |
| `fullscreen` | เต็มหน้าจอสมบูรณ์ ซ่อนแถบสถานะ (status bar) ของระบบปฏิบัติการ |
| `standalone` | ซ่อน Address Bar และปุ่มควบคุมของเบราว์เซอร์ แต่ยังคงเห็น status bar ของระบบ (โหมดยอดนิยมสำหรับ PWA) |
| `minimal-ui` | มีแถบเบราว์เซอร์ขนาดเล็ก แสดงเฉพาะปุ่มย้อนกลับและรีเฟรช |
| `browser` | เปิดเหมือนเว็บไซต์ปกติในแท็บเบราว์เซอร์ทั่วไป (ค่าเริ่มต้นหากไม่ระบุ) |

### 2.2 Maskable Icon และ Safe Zone

ระบบปฏิบัติการ (โดยเฉพาะ Android) มักครอบตัดไอคอนแอปเป็นรูปทรงต่าง ๆ เช่น วงกลม สี่เหลี่ยมมุมโค้ง หรือหยดน้ำ ตามธีมของเครื่อง หากเราใช้โลโก้แบบเต็มขอบ ไอคอนอาจโดนตัดส่วนสำคัญไป

> [!TIP]
> สำหรับไอคอนที่ตั้งค่า `"purpose": "maskable"` ควรออกแบบให้ส่วนประกอบสำคัญ (โลโก้หรือตัวอักษร) อยู่ภายในพื้นที่ **Safe Zone** (ตรงกลาง 80% ของภาพ) ส่วนที่เหลือปล่อยให้เป็นสีพื้นหลังเต็มขอบ เพื่อให้แสดงผลได้สวยงามไม่ว่าจะถูกครอบตัดด้วยรูปทรงใดก็ตาม

## 3. Service Worker

**Service Worker (SW)** คือสคริปต์ JavaScript พิเศษที่ทำงานแยกจากหน้าเว็บหลัก (ทำงานใน Background Thread มี Lifecycle และ Scope ของตัวเอง ไม่สามารถเข้าถึง DOM ได้โดยตรง) หน้าที่หลักคือดักจับ network request ทุกตัว แล้วทำการเลือกว่าจะดึงข้อมูลจาก **Cache** หรือ **Network** มาแสดงผล

### 3.1 วงจรชีวิตของ Service Worker (Lifecycle)

1.  **Register** — สั่งให้เบราว์เซอร์ทำการลงทะเบียน Service Worker (`navigator.serviceWorker.register('/sw.js')`)
2.  **Install** — ดาวน์โหลดสคริปต์และรัน event `install` มักใช้ช่วงนี้เพื่อทำ Precache ไฟล์ static ที่จำเป็นสำหรับการโหลดแอปเริ่มต้น
3.  **Activate** — Service Worker เวอร์ชันใหม่พร้อมควบคุมหน้าเว็บ มักใช้ล้าง Cache ของเวอร์ชันเก่าทิ้ง
4.  **Fetch** — เกิดขึ้นเมื่อหน้าเว็บมีการเรียกข้อมูล (request) โดย Event `fetch` จะถูกเรียกเพื่อจัดการผลลัพธ์ที่จะตอบกลับ

### 3.2 กลยุทธ์การแคชข้อมูล (Caching Strategies)

การเลือกกลยุทธ์การแคชที่ถูกต้องเป็นหัวใจสำคัญในการทำงานแบบออฟไลน์:

| กลยุทธ์ | พฤติกรรม | เหมาะสำหรับ |
| :--- | :--- | :--- |
| **Cache First** | ค้นหาใน Cache ก่อน ถ้ามีให้ส่งคืนทันที ถ้าไม่มีค่อยดึงจาก Network | ไฟล์ static ที่ไม่มีการเปลี่ยนแปลงบ่อย เช่น ฟอนต์, ไอคอน หรือ JS/CSS ที่มี hash ต่อท้าย |
| **Network First** | ดึงข้อมูลจาก Network ก่อน หากล้มเหลว (Offline) ค่อยดึงข้อมูลเก่าจาก Cache มาแสดงแทน | ข้อมูลหรือหน้า HTML ที่ต้องการความสดใหม่เสมอ แต่ต้องการให้เปิดดูข้อมูลเก่าได้ตอนออฟไลน์ |
| **Stale-While-Revalidate** | ส่งข้อมูลจาก Cache ไปแสดงผลทันที (โหลดเร็วมาก) พร้อมกับแอบส่ง request ไป Network เพื่อดึงข้อมูลใหม่มาอัปเดตแคชไว้สำหรับครั้งถัดไป | ข้อมูลที่อัปเดตบ่อยแต่ไม่ใช่เรื่องคอขาดบาดตาย เช่น รูปโปรไฟล์ หรือบทความหน้าแรก |
| **Network Only** | ดึงข้อมูลจาก Network เท่านั้น ไม่บันทึกหรือเช็คใน Cache เลย | ข้อมูลที่มีความเสี่ยงหรือต้องการความถูกต้องสูงสุด เช่น ยอดเงินคงเหลือ, ข้อมูล API ส่วนบุคคล |
| **Cache Only** | ดึงจาก Cache เท่านั้น ไม่แตะเน็ตเลย | ข้อมูลที่ถูกเตรียมไว้ล่วงหน้าในขั้นตอนติดตั้ง (Precached) และไม่มีวันเปลี่ยน |

> [!WARNING]
> ห้ามใช้กลยุทธ์ **Cache First** หรือ **Stale-While-Revalidate** กับ endpoint API ที่ส่งคืนข้อมูลส่วนบุคคล (เช่น ข้อมูลบัญชีผู้ใช้, ยอดเงิน) เนื่องจากอาจทำให้ผู้ใช้เห็นข้อมูลของคนอื่นที่ล็อกอินในเครื่องสาธารณะเดียวกันผ่านประวัติแคชที่ตกค้าง

### 3.3 ตัวอย่างการเขียน Service Worker เบื้องต้น (Vanilla JavaScript)

```javascript
const CACHE_NAME = "shell-v1";
const SHELL_FILES = ["/", "/styles.css", "/app.js"];

// ติดตั้ง: โหลดไฟล์โครงสร้าง (Shell) เก็บไว้ล่วงหน้า
self.addEventListener("install", (event) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then((cache) => cache.addAll(SHELL_FILES))
  );
});

// ดักจับ request: ใช้กลยุทธ์ Cache First
self.addEventListener("fetch", (event) => {
  event.respondWith(
    caches.match(event.request).then((cached) => cached || fetch(event.request))
  );
});
```

ในการใช้งานจริง เรามักไม่นิยมเขียนโค้ด Service Worker ดิบทั้งหมดเองเนื่องจากมีจุดที่ต้องระวังและจัดการเรื่อง Cache Versioning ค่อนข้างยาก แต่มักนิยมหันมาใช้ไลบรารีช่วยจัดการแทน (ดูข้อ 5)

## 4. เกณฑ์การรองรับการติดตั้งแอป (Installability Criteria)

เบราว์เซอร์จะแสดงปุ่มให้ติดตั้งแอป (Install App) หรือขึ้นหน้าต่างเตือนติดตั้ง ก็ต่อเมื่อเว็บไซต์ผ่านเงื่อนไขดังต่อไปนี้:

*   [ ] ให้บริการผ่านระบบรักษาความปลอดภัย **HTTPS** (`localhost` ได้รับการยกเว้นตอนพัฒนา)
*   [ ] มีไฟล์ **Web App Manifest** ที่มีรูปแบบถูกต้อง และระบุฟิลด์ที่จำเป็นครบถ้วน (`name`, `icons`, `start_url`, `display: standalone/fullscreen/minimal-ui`)
*   [ ] มีการลงทะเบียน **Service Worker** สำเร็จ และมี event handler สำหรับจัดการ `fetch` อยู่จริง
*   [ ] ผู้ใช้งานมีส่วนร่วมกับเว็บระยะหนึ่ง (User Engagement) เช่น การเลื่อนหรือการคลิกหน้าเว็บ

> [!NOTE]
> สำหรับ **iOS Safari** จะไม่มีหน้าต่างขึ้นเตือนให้ติดตั้งแอปโดยอัตโนมัติ ผู้ใช้ต้องกดปุ่ม Share (แชร์) แล้วเลือกหัวข้อ "Add to Home Screen" (เพิ่มไปยังหน้าจอโฮม) ด้วยตนเองเสมอ และมีความสามารถ PWA บางฟังก์ชันที่ iOS ยังไม่รองรับเต็มที่ จึงจำเป็นต้องทดสอบบนอุปกรณ์จริงร่วมด้วยเสมอ

## 5. เครื่องมือช่วยจัดการบน Next.js: Serwist / Workbox

การเขียนโค้ดควบคุม Service Worker ด้วยตนเองเสี่ยงที่จะเกิดความผิดพลาดได้ง่าย (เช่น ผู้ใช้เปิดใช้งานแต่ได้หน้าเว็บเวอร์ชันเก่าค้างอยู่ตลอดกาล) นักพัฒนาจึงมักใช้ไลบรารีที่สร้างครอบครอบ Workbox ของ Google สำหรับโปรเจกต์ Next.js (App Router) ไลบรารีที่เป็นที่นิยมในปัจจุบันคือ **[Serwist](https://serwist.pages.dev/)**

การทำงานของ Serwist:
1.  เราเขียนสคริปต์ Service Worker เบื้องต้น (เช่น `app/sw.ts`) เพื่อกำหนดนโยบายการทำงานของ Cache
2.  ขั้นตอน Build ระบบจะสแกนหาไฟล์ static และไฟล์โค้ดทั้งหมดที่สร้างจาก Next.js แล้วนำรายชื่อไฟล์ไปฉีดใส่ตัวแปร `self.__SW_MANIFEST` เพื่อลงทะเบียน Precache ให้อัตโนมัติ
3.  ได้ผลลัพธ์เป็นไฟล์ `public/sw.js` พร้อมใช้งาน

```typescript
// app/sw.ts (ตัวอย่างการเขียนด้วย Serwist)
import type { PrecacheEntry, SerwistGlobalConfig } from "serwist";
import { NetworkFirst, Serwist } from "serwist";

declare global {
  interface WorkerGlobalScope extends SerwistGlobalConfig {
    __SW_MANIFEST: (PrecacheEntry | string)[] | undefined;
  }
}
declare const self: ServiceWorkerGlobalScope;

const serwist = new Serwist({
  precacheEntries: self.__SW_MANIFEST, // นำรายชื่อไฟล์ที่แสกนได้มาลงแคชทันที
  skipWaiting: true,
  clientsClaim: true,
  runtimeCaching: [
    {
      // กำหนดให้การเปลี่ยนหน้าเว็บ (Navigation) ใช้กลยุทธ์ Network First
      matcher: ({ request, sameOrigin }) => sameOrigin && request.mode === "navigate",
      handler: new NetworkFirst({ cacheName: "shell-pages" }),
    },
  ],
});

serwist.addEventListeners();
```

> [!WARNING]
> **ข้อควรระวังเรื่อง Bundler (Next.js 15+):** Next.js ในเวอร์ชันใหม่มีการขยับไปใช้งาน **Turbopack** เป็นตัวช่วยประมวลผลดั้งเดิม ซึ่งปลั๊กอินของ Serwist หรือเครื่องมือ PWA บางตัวยังไม่อาจสนับสนุน Turbopack ได้เต็มที่ในขั้นตอน build วิธีการแก้ไขคือการปิดใช้งาน PWA ในโหมด Development (ซึ่งช่วยประหยัดเวลาการทำ Cache อยู่แล้ว) และใช้ webpack เฉพาะในขั้นตอน build จริงผ่านคำสั่ง `next build --webpack`

## 6. การวางแผนความสามารถในการทำงานแบบออฟไลน์ (Offline Strategy)

ก่อนตัดสินใจเริ่มเขียนโค้ด ควรออกแบบระดับการทำงานแบบออฟไลน์ตามความจำเป็นของโครงการ เพื่อลดความซับซ้อนของโค้ดที่ไม่จำเป็น:

| ระดับความสามารถ | รายละเอียดการทำงาน | ความซับซ้อน |
| :--- | :--- | :--- |
| **Online-only + Installable shell** | โหลดหน้าแอปเปล่า ๆ และไฟล์สไตล์สระขึ้นมาได้แม้ไม่มีเน็ต แต่ข้อมูลเนื้อหาภายในต้องเชื่อมอินเทอร์เน็ตถึงจะแสดงผลได้ | **ต่ำ** (แนะนำสำหรับ MVP ส่วนใหญ่) |
| **Offline-first แบบอ่านอย่างเดียว (Read-only)** | แคชข้อมูลชุดล่าสุดเก็บลงฐานข้อมูลจำลองในบราวเซอร์ (IndexedDB) เพื่อให้ผู้ใช้เปิดดูข้อมูลล่าสุดได้แม้ไม่มีเน็ต แต่ยังเพิ่มหรือแก้ไขข้อมูลไม่ได้ | **ปานกลาง** |
| **Offline-first แบบสมบูรณ์ (Write & Sync)** | ให้ผู้ใช้แก้ไขหรือเขียนข้อมูลเพิ่มได้แม้ปิดเน็ต โดยแอปจะเก็บคำสั่งเข้าคิวรอส่งขึ้นเซิร์ฟเวอร์เมื่อเน็ตกลับมาทำงาน มีความเสี่ยงในการชนกันของข้อมูล (Conflict) | **สูงมาก** |

## 7. ขั้นตอนการเริ่มเปิดใช้งาน PWA ในโปรเจกต์ Next.js (App Router)

**ขั้นตอนที่ 1: ติดตั้งแพ็กเกจ**
```bash
pnpm add serwist @serwist/next
```

**ขั้นตอนที่ 2: สร้างไฟล์ Manifest**
สร้างไฟล์ `app/manifest.ts` และเขียนการส่งออกข้อมูล Object ในรูปแบบตามข้อ 2 โดย Next.js จะแปลงไฟล์นี้ให้อยู่ในรูป `/manifest.webmanifest` และแปะลิงก์ใส่ Header ของ HTML ให้อัตโนมัติ

**ขั้นตอนที่ 3: สร้างไฟล์สคริปต์ Service Worker**
สร้างไฟล์ `app/sw.ts` เพื่อเขียนโค้ดควบคุม Lifecycle และกำหนดกลยุทธ์การทำงานของข้อมูลแคชตามแนวทางของระบบ

**ขั้นตอนที่ 4: ตั้งค่าคอนฟิกของ Next.js**
นำ Serwist เข้าไปประกาศครอบ config ในไฟล์ `next.config.ts`:
```typescript
import withSerwistInit from "@serwist/next";

const withSerwist = withSerwistInit({
  swSrc: "app/sw.ts",
  swDest: "public/sw.js",
  disable: process.env.NODE_ENV !== "production", // ปิดแคชตอนกำลังพัฒนาในเครื่อง
});

export default withSerwist(nextConfig);
```

**ขั้นตอนที่ 5: เตรียมไฟล์ไอคอนต่าง ๆ**
จัดวางไฟล์ไอคอนให้ครบถ้วนในโฟลเดอร์ `public/` โดยเฉพาะขนาดที่ต้องใช้งานบน iOS (`apple-touch-icon`) จากนั้นระบุรายละเอียดไอคอนใน metadata ของหน้า Layout:
```typescript
export const metadata: Metadata = {
  icons: { apple: "/icons/apple-touch-icon.png" },
  appleWebApp: { capable: true, statusBarStyle: "default", title: "My App" },
};
export const viewport: Viewport = { themeColor: "#0ea5e9" };
```

**ขั้นตอนที่ 6: ปิดการใช้งาน Turbopack ชั่วคราวเฉพาะตอน Build (หากเกิดปัญหา)**
ปรับเปลี่ยนคำสั่ง Build ใน `package.json` หากไลบรารีที่ใช้งานมีปัญหากับ Turbopack:
```json
{
  "scripts": {
    "build": "next build --webpack"
  }
}
```

**ขั้นตอนที่ 7: อัปเดตไฟล์ `.gitignore`**
ป้องกันไม่ให้มีการบันทึกไฟล์สคริปต์ Service Worker ที่สร้างขึ้นตอน build เข้าไปยัง git repository:
```
/public/sw.js
/public/sw.js.map
```

**ขั้นตอนที่ 8: ทำการ Build เพื่อทดสอบจริง**
```bash
pnpm build
pnpm start
```
จากนั้นเปิดไปที่ URL และทดสอบระบบความปลอดภัยด้วยเครื่องมือในเบราว์เซอร์

## 8. ข้อควรระวังและแนวทางปฏิบัติที่ดีที่สุด (Best Practices)

1.  **เลือกประเภทข้อมูลที่แคชอย่างระมัดระวัง:** หลีกเลี่ยงการแคชข้อมูลที่มีผลลัพธ์เป็นความลับหรือข้อมูลเฉพาะของผู้ใช้งาน
2.  **ระวังการดักจับข้อมูลต่าง Domain:** ตรวจสอบว่าเงื่อนไข `runtimeCaching` match เฉพาะ request ที่วิ่งมาที่เว็บของเรา ไม่ใช่ไปแอบจับและแคช request ที่ยิงออกไปยัง API นอกระบบโดยไม่ตั้งใจ
3.  **จัดการเคลียร์ Service Worker เก่า:** ออกแบบขั้นตอนการแจ้งเตือนผู้ใช้งานเพื่อให้รีเฟรชหน้าเว็บเมื่อมี Service Worker ตัวใหม่ที่เพิ่งปล่อยใช้งานเสร็จ (เพื่ออัปเกรดแอปให้เป็นรุ่นปัจจุบันเสมอ)

## 9. การทดสอบและการ Debug ระบบ PWA

*   **แท็บ Application ใน Chrome DevTools:**
    *   **Manifest:** ใช้ตรวจสอบความถูกต้องและทดลองกดจำลองการติดตั้ง
    *   **Service Workers:** ดูสถานะการเชื่อมต่อ และสามารถกดสั่งหยุด (Unregister) หรืออัปเดตสคริปต์ระหว่างทดสอบได้ทันที
    *   **Cache Storage:** ใช้ส่องข้อมูลภายในของไฟล์แคชแต่ละก้อนว่าเก็บข้อมูลได้ถูกต้องตามที่เขียนไว้หรือไม่
*   **เครื่องมือ Lighthouse (ใน Chrome DevTools):**
    *   สร้างรายงานในหัวข้อ **Progressive Web App** เพื่อตรวจสอบว่ายังขาดองค์ประกอบใดในการทำให้แอปสมบูรณ์แบบ
*   **ทดสอบบนอุปกรณ์จริง:** หน้าตาการทำงานและความปลอดภัยของ iOS Safari และ Android Chrome จะมีรายละเอียดการตอบสนองที่ต่างกัน การจำลองด้วย Device Mode บนคอมพิวเตอร์อย่างเดียวไม่อาจยืนยันผลการติดตั้งของฝั่งสมาร์ทโฟนได้จริง

## 10. รายการเช็คลิสต์ตรวจความพร้อม (PWA Readiness Checklist)

*   [ ] มี Manifest ครบถ้วน (รวมถึงไอคอนขนาด 192px/512px และ standalone display)
*   [ ] จัดเตรียมไอคอนเฉพาะสำหรับอุปกรณ์ iOS และกำหนด Safe Zone สำหรับ Maskable Icon เรียบร้อย
*   [ ] Service Worker ทำการเชื่อมต่อสำเร็จและสามารถดักจับ Fetch Event ได้
*   [ ] ตั้งค่า Caching logic โดยไม่เกิดการรั่วไหลของข้อมูลที่เป็นความลับ
*   [ ] ทดสอบจำลองการเข้าใช้งานขณะตัดอินเทอร์เน็ต (Offline Mode) หน้าต่างหรือโครงหน้าแอปหลักยังแสดงผลได้
*   [ ] รันตรวจสอบผ่าน Lighthouse PWA Audit แล้วผ่านเงื่อนไขทั้งหมด
*   [ ] ให้บริการผ่าน HTTPS ในระบบ Production จริง
